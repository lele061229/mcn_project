## 2. 用户点击按钮后的完整执行链路

以「发起交接」为例（本项目最有代表性的一条链路）：

```
[用户] 达人列表点「交接」按钮
   ↓
[index.html] 交接弹窗打开（v-if="dlg.id==='handover'"），渲染 8 个表单字段
   ↓
[talent-leads.js] 用户填完点「提交」→ saveHandover(onToast)
   ├─ 前端校验：toUser 非空；CL 开头 ID 是演示数据 → 只改本地状态直接返回
   └─ fetch('POST /api/mvp/handovers', { talentId, toUser, situation, risk, ... 10 个字段 })
   ↓
[v1/server.js] route('POST','/api/mvp/handovers', createHandover)
   ├─ 鉴权：ctx.role.mutate（财务等只读角色 403）
   ├─ findLeadOrTalent(id)：先查 leads 表、再查 talents 表（转化后 ID 不变）
   ├─ canTouchLead()：只有当前负责人本人或管理员可发起
   ├─ 业务边界：接收岗位必须在 OWNER_POSITIONS（招募/运营），寄拍/财务岗 400
   ├─ db.insert('handovers', 交接单) —— 注意：此时负责人还没变！
   ├─ db.update(coll, ...handoverStatus:'pending'...) 只挂「待确认」标记
   ├─ addLog(...) 写操作日志 + notify(...) 站内通知
   └─ ok(res, toHandover(rec)) 返回 JSON
   ↓
[talent-leads.js] then(j => ...)：j.ok 检查 → 本地更新 r.handoverStatus='pending' → 关弹窗 → toast
   ↓
[接收人登录] 工作台「待确认交接」卡片 → confirmHandover()
   → POST /api/mvp/handovers/:id/confirm
   → 服务端确认后才 db.update 改 owner/ownerPosition/ownerId
   → 若接收人是 ops：同时固化 opsBy/opsId/opsAt（opsPending 自动消失）
```

**这个项目的通用链路模式**（所有按钮都长这样）：

1. 前端方法做**第一道校验**（必填、演示数据短路）；
2. `fetch` 到 `/api/mvp/...`；
3. 服务端做**第二道（真正的）权限与边界校验** —— 前端隐藏菜单只是展示层，服务端 403/400 才是安全边界；
4. 写库 + `addLog` 留痕 + `notify`；
5. `ok(res, data)` 统一响应格式 `{ok:true, data}` / `fail(res, code, msg)` 的 `{ok:false, error}`；
6. 前端 `then` 里**乐观更新本地状态**（不整页刷新）。

## 3. 最核心的 5 段代码（位置 + 逐块解释）

### ① 负责人三分离 + opsPending 派生 —— `v1/server.js:716-752`（toMvpLead）

```js
opsBy: t.opsBy || '', opsId: t.opsId || '', opsAt: String(t.opsAt || ''),
// 待运营接收：已转正式（合作中）但负责人还是招募岗、且没固化运营负责人
opsPending: ['合作中', '暂停合作'].includes(t.status) && t.ownerPosition !== 'ops' && !t.opsId,
```

- **`owner/ownerId/ownerPosition`**：当前负责人，随每次交接实时变化。
- **`opsBy/opsId/opsAt`**：运营归属，交接确认给运营岗那一刻**固化**，之后再交接也不变（用于业绩归属）。
- **`recruitBy`**：原招募负责人，转正前记录。
- **`opsPending` 是派生字段，不落库**：每次读列表时由上面三个条件现算。三个条件缺一不可 —— ①状态已合作 ②当前负责人不是运营岗 ③还没固化 opsId。这意味着你**永远不需要写代码去"更新 opsPending"**，只要 owner/opsId 变了它自动对。

### ② 转化不变量 promoteToTalent —— `v1/server.js:1006-1038`

```js
async function promoteToTalent(merged, operatorName, operatorId, fromStatus, extraLog) {
  const rec = Object.assign({}, merged, {
    status: '合作中',
    convertedBy: merged.convertedBy || operatorName || '',
    convertedAt: merged.convertedAt || nowT,
    nextFollowAt: '',   // 转化后不再挂在「今日待跟进」里
  });
  if (rec.ownerPosition === 'ops' && !rec.opsId && rec.ownerId) {
    rec.opsBy = rec.owner; rec.opsId = rec.ownerId;   // 负责人本来就是运营岗 → 顺手固化
  }
  await db.remove('leads', rec.id);   // 从线索池删
  await db.insert('talents', rec);    // 进达人库，ID 不变
  ...
}
```

- 这是**双表模型的唯一入口**：所有把线索推到「合作中」的路径（convert 接口、PUT 改状态、跟进推送）最终都必须走这个函数，它保证 `convertedBy/convertedAt` 一定留痕、leads/talents 两表不漂移。
- **绝对不要绕过它手写 `db.remove('leads')+db.insert('talents')`**。
- 注意 ID 不变：线索 T0004 转正后还是 T0004，所以交接等操作要靠 `findLeadOrTalent()`（server.js:1086，先查 leads 再查 talents）双表定位。

### ③ 交接单 createHandover —— `v1/server.js:1133-1186`

```js
if (!OWNER_POSITIONS.includes(toPosition)) {
  return fail(ctx.res, 400, '「' + posLabel(toPosition) + '」岗不做达人负责人...');
}
const rec = {
  situation: ..., accountState: ..., coopWay: ...,
  contentDirection: ..., risk: ..., nextSuggest: ...,   // 7 个结构化知识传递字段
  status: 'pending', ...
};
await db.insert('handovers', rec);
await db.update(coll, t.id, { handoverStatus: 'pending', ... handoverRisk: rec.risk });
```

- **关键设计：发起交接 ≠ 变更负责人**。发起时只写 `handovers` 集合 + 在达人/线索上挂 `handoverStatus:'pending'`，负责人仍是原负责人；接收人 confirm（server.js:1191 的 `/handovers/:id/:action`）后才改 owner。这样交接期间原负责人照常工作，驳回也零成本。
- 7 个结构化字段（情况/账号/合作方式/内容方向/风险/下一步建议）是招募→运营的知识传递载体，`risk` 会同步一份到 `handoverRisk` 供列表直接看。
- 每个 slice(0,N) 是防脏数据撑爆 JSON 库。

### ④ 任务派生字段 annotateTask —— `v1/server.js:2029-2061`

```js
overdue: active && !!k.dueAt && k.dueAt < today,
dueSoon: active && !!k.dueAt && k.dueAt >= today && k.dueAt <= fmtDate(new Date(Date.now() + 2 * 86400000)),
```

- `overdue/dueSoon` 和 opsPending 一样是**读时派生**，不落库 —— 截止时间一过自动"变逾期"，不需要定时任务。
- `GET /api/tasks`（2042-2061）是**行级权限的教科书**：管理员全量 → 寄拍岗只看"执行人是我" → 运营只看"我名下达人"（先算出我的 talentId 集合再过滤）→ 其他岗位直接 403。**权限永远在服务端裁决，前端 `v-if` 藏按钮只是体验优化。**

### ⑤ 看板风险提醒 alerts —— `v1/server.js:1588-1614`

```js
const alerts = [];
if (unassigned) alerts.push({ type: '未分配线索', count: unassigned, text: '...', page: 'talent-leads', tone: 'rose' });
...
ok(ctx.res, { ..., alerts, ... });
```

- 每条 alert 是 `{type, count, text, page, tone}`：`page` 告诉前端点了跳哪个菜单页，`tone`（rose/amber/teal）决定颜色严重度。
- 前端 `app.js:664` 的 `boardAttention`/`boardAlerts` computed 只做消费渲染，不做计算 —— **所有业务口径集中在 server.js 一处**，改口径只改后端。
- 注意 1588 附近 Date 解析是**内联**的，不要引用工作台路由里的 `ts` 变量（作用域不同，会运行时 ReferenceError——这个坑踩过）。

### 附：前端侧对应代码 `talent-leads.js:601-628`（saveHandover）

前端 fetch 发起交接的完整样例：必填校验 → `CL` 前缀演示数据短路（不碰后端）→ POST 全部 10 个字段 → `j.ok` 检查 → 本地更新 `r.handoverStatus` → toast。看懂这一个就看懂了项目里所有"提交表单"的写法。

## 5. 出 Bug 时先检查哪里（按命中率排序）

1. **前端改了但行为没变** → `index.html` 里 `?v=` 版本号没 +1，浏览器拿的旧缓存。这是本项目第一名 Bug。
2. **接口 403/400** → 不是 Bug，是服务端权限/边界在正确工作。用出问题的那个**账号**登录测（不要用 admin 测员工功能），检查 `isMine`/`canTouchLead`/`ctx.position`。
3. **列表字段不对/口径不一致** → 查 `toMvpLead()`（所有列表的统一出口）。字段在 db.json 里有但接口没吐，八成是这里漏了映射。
4. **改了 server.js 线上没生效** → 忘了 `systemctl restart mcn-admin`。改后端必须重启，改前端不用。
5. **回归脚本大面积诡异失败但 curl 正常** → 残留的旧 headless Edge 占着 9290 端口。`netstat -ano | grep :9290` 查杀重跑。
6. **转化/双表相关** → 检查是否绕过了 `promoteToTalent`；跨表查询是否用了 `listLeadsAndTalents()`/`findLeadOrTalent()`。
7. **数据字段缺失** → `migrateDb()` 启动自愈是否覆盖了新字段；看 `v1/data/db.json` 原始数据（别只信界面）。
8. **分页断言失败** → 回归脚本数 `<tr>` 是错的（每页 10 行），要看页脚"共 N 条"。

**排查顺序**：复现（哪个账号哪个页面）→ 打开 F12 Network 看接口返回的是 403/400 还是数据错 → 数据错查 server.js 对应 route → 显示错查 index.html 对应区块 + `?v=` 版本号。改完必跑回归：`python v1/check-biz-chain.py`（业务链 28 项）+ `python v1/check-crm-api.py`（176 项）。
