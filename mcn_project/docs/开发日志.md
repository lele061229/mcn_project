## 2026-09-18 线索字段分层：报名只产映射字段，判断字段由运营判定（v20260918d）

**业务问题**：报名表提交的线索，评级/潜力/合作意愿/分类/合作路径这些「运营判断」字段不该直接有值——报名信息不足以判断。

**三层模型**（学习点：把「数据来源」和「数据裁决」分开，字段才有可信度）：
1. **报名表映射字段**（公开接口 POST /api/leads 只写这些）：昵称→name、来源渠道→channel、自媒体→recruit.selfMedia、合作经历→recruit.hasExp、想接品类→recruit.preferredCategories、出镜方式→recruit.appearWay、作品→recruit.works、想了解→recruit.questions、phone/wechat→contact。
2. **初始化规则**：新报名/新线索 → 阶段=新线索、talentStatus=lead、评级=「待判断」（新合法值 TALENT_LEVEL_UNSET，进 TALENT_LEVEL_ANY，migrate 不再覆写）、潜力/意愿=待判断、分类=待分类、路径=待判断。
3. **判断字段权限** canJudgeLead(ctx)=isSupervisor(ctx)||position==='ops'（普通运营/高级运营/管理员）：PUT /api/mvp/leads 判断字段 403、talent-meta 评级 403、跟进接口静默剥离判断字段；创建线索时只有可判岗位能显式带评级（SLA 造数场景）。招募岗在弹窗里看不到判断字段控件（前端 tl.canJudge 与服务端同口径）。

**回归**：check-crm-api +13 项 → 189（报名映射×2、初始化×2、招募 403×2、跟进剥离×2、运营/主管/管理员放行×2、行级隔离×1、前置分配×1）；全量 465 项本地+线上全绿。坑：报名公开接口返回 {code:0} 不是标准 {ok:true}，测试解析别读错。

## 2026-09-18 · 高级运营分配达人给普通运营（talentOperator + 分配记录）

**需求**：senior_ops 在达人档案页 / 线索页把达人分配给普通运营；ops 工作台新增「新分配达人 / 我的达人 / 待跟进提醒」；分配写独立记录可回溯；ops 只看自己名下达人。

**学到的设计点**：
- **复用而非新造**：项目里早就有 `POST /api/mvp/leads/:id/assign`（isSupervisor 校验 + OWNER_POSITIONS 岗位边界 + SLA 重计时），这次没有新建接口，而是修它的一个真 Bug——旧代码只在 `!t.opsId` 时写 `talentOperator`，导致**重新分配给另一位普通运营时 talentOperator 残留旧人**。改成 `toPosition==='ops'` 时始终刷新（opsBy/opsId/opsAt/talentOperator 四件套）。
- **分配记录独立成集合** `talentAssignments`：{talentId/talentName, fromOwner/Id, toOwner/Id, type, remark, assignedBy/Id, assignedAt}。谁把达人分给了谁、备注是什么，一眼可查；同时把分配记录**并入跟进时间轴**（`GET /api/mvp/leads/:id/follow-ups` 的返回里混入 type=分配 的行），前端零改动就能看到交接历史。
- **级联清理要成对出现**：删线索、删达人档案都必须级联删 talentAssignments，否则又是孤儿记录挂到将来复用的 ID 上（跟 followups 孤儿是同一个坑）。
- **ops 工作台新面板**是服务端 buildWorkbenchPanels 装配的（new-assigned 表格 / follow-remind 提醒），前端纯渲染没改一行。
- **回归断言要跟着数据口径走**：时间轴并入分配记录后，老断言「读回的第一条是跟进内容」会翻车（分配记录可能排在前面），改成 any() 语义断言。

**改动文件**：`v1/server.js`（doAssign 修 Bug + 写分配记录 + GET assignments + 时间轴合并 + 两处级联 + ops 面板）、`talent-leads.js`（分配弹窗备注字段 + 弹窗带行数据）、`index.html`（达人档案页「分配给运营」按钮 + 弹窗备注框 + 版本号 20260918a）、`v1/check-crm-api.py`（新增 17 项 → 166）。

**验证**：本地全量 442 项全绿（166+28+26+44+40+15+75+48）；线上 check-crm-api 166 项全绿、check-crm-ui 48 项全绿（首跑 5 项失败为冷启动假失败，复跑即绿）。临时测试账号已清理，auth.json 保持 6 账号。

7. **根因修复**（`v1/check-perm.js`，属回归脚本、非业务代码）：脚本用已删除的岗位值造账号 `{user:'demo-sample', position:'sample'}`，而 `server.js:3328` 对非法岗位的处理是「归一化为空字符串」→ 每次跑回归都重新造出一个 `position:''` 的幽灵账号。改为使用现役推广岗 `demo-promote`，断言文案同步改为「推广岗…」，断言条数不变。

**验证**：本地全量回归全绿——check-crm-api **149** / biz-chain 28 / v03-core 26 / perm 44 / sla 40 / split-smoke 15 / demo-roles 75 / crm-ui 48（合计 425）。删账号后登录探测：`demo-sample` → **401**，其余 5 个 demo 账号均 200；`GET /api/users` 本地与线上都只返回 6 个账号。改完 check-perm 再跑一轮，跑完 `auth.json` 仍是 6 个账号（幽灵不再复活）。

**踩坑记录**：

1. **文档是 CRLF**！md 文件行尾是 `\r\n`（不是源码那种 LF），按 `\n` 拼替换锚点会「0 匹配」——批量替换前先探测行尾，脚本里统一换算。
2. **改 auth.json 必须重启服务**：`AUTH` 只在启动时 `JSON.parse` 一次（server.js:3178-3180），只改文件不重启，接口仍按内存里的旧账号表判定。
3. **改本地 auth.json 前先停本地服务**：跑过 `check-perm.js` 后幽灵账号已被服务端写回文件，「以为清理干净了」其实又变回 7 个——先停服务 → 再清理 → 再部署。

**学习价值**：①「文档与代码冲突」的正解是**以代码为准改文档**（本轮 4 项全是文档错）；②一个 `POSITIONS.includes(...)` 的静默兜底（非法值归一为空串）会造出「看起来合法」的脏数据，服务端校验宁可 400 也不要静默兜底；③回归脚本自己会造数据，**改账号/角色模型时必须连脚本一起过一遍**，否则脚本本身就是脏数据来源。
